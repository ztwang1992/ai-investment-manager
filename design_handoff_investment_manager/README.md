# Handoff：个人投资管理器（PWA）· v5

## 概述
这是一个手机优先的个人投资管理网页 App（PWA）。核心能力：
- 把分散在多个券商、多个市场的持仓按**底层资产**穿透合并。例如 VOO、513500、博时标普 QDII 都算作「标普 500」。
- 目标组合直接设在底层资产上，对照目标显示偏离，并支持三种调整方式：再平衡、增量投入（只买不卖）、取钱（先卖超配最多的）。
- 收益曲线分开画总资产和净投入本金；每季度提醒核对持仓份额；内置接入用户自己 DeepSeek Key 的 AI 投顾。

## 关于设计文件
`投资管理器 原型 v5.dc.html` 是**用 HTML 做的设计参考**，用来演示外观和交互，**不是**可以直接上线的代码。请用 **React + Vite（PWA）** 重新实现。
原型里的这些内容都是写死或模拟的：示例持仓、行情、汇率、5 年历史曲线、每项资产的区间涨跌幅。真实版本要从 Supabase 读取用户数据，并通过 Cloudflare Worker 拉取行情和汇率。

## 保真度
**高保真**。颜色、字体、圆角、间距以原型为准。

## 技术栈（已确定）
- **前端**：React + Vite，PWA（manifest + service worker），本地缓存用 IndexedDB
  - 本地优先：完整数据在手机本地存一份，离线也能查看和记账，联网后自动同步（见「数据模型 · 本地优先与同步」）
- **部署**：Cloudflare Pages + Worker，**都绑定自己的域名**（例如 app.<域名>、api.<域名>）
  - `*.workers.dev` 在国内基本打不开，`*.pages.dev` 也不稳定，所以不用默认域名
  - 域名在腾讯云购买并完成实名认证，DNS 服务器改成 Cloudflare 分配的地址（Cloudflare 免费版只支持这种接入方式）。服务器不在国内，不需要备案
- **行情/汇率**：由 Cloudflare Worker 中转，结果缓存 15 分钟，只用免费数据源（阶段 0 先在 Worker 里实测候选接口再定）。场外基金用 T-1 净值。
- **数据与登录**：Supabase（新加坡或东京区），全部表开启 RLS
  - 登录用邮箱 6 位验证码（OTP），不用 magic link：iPhone 上添加到主屏幕的 App 和 Safari 的存储是隔离的，点邮件里的链接只会在 Safari 里登录
  - 配置自定义 SMTP：Supabase 自带的邮件服务每小时只能发几封，只适合测试
- **AI 投顾**：第一期只支持 DeepSeek（OpenAI 兼容格式，地址 `https://api.deepseek.com`，模型 `deepseek-chat`）
  - 用户自己的 Key 加密后只保存在本机
  - 连通性测试和对话请求由浏览器直接发给 DeepSeek（它允许跨域调用），Key 不经过我们的服务器
- **其他约束**：不办 ICP 备案，国内能访问即可；从一开始按多用户设计

## 增量投入算法（「投入一笔钱」）
**输入**：金额、币种（人民币 / 美元），以及模式 ——「只在一个账户买」（要选账户）或「可跨账户」。

1. 候选槽位：目标 > 0，且有**同币种**可买品种的槽位。「只在一个账户买」模式下，品种还必须能在这个账户里买到（按市场匹配：美元券商 → 美股，人民币券商 → A 股，银行 → 场外基金）。
2. 投入后总资产 T2 = 当前总资产 + 投入金额。
3. **按"注水"方式分配**：找一个水位 L，让 Σ max(0, L × 目标% − 当前市值) 刚好等于投入金额（二分法求 L）。这样低配越严重（当前市值 ÷ 目标比例越低）的槽位越先补齐，被买入的槽位投入后都不会超过目标比例（钱多到能把所有候选补到目标时，按第 4 步处理）。
   - **被买入的槽位不被稀释**：总资产变大了，买得少的槽位占比可能反而比投入前低。这样的一笔不买，钱改投更低配的槽位；更低配的放不下（会超过目标）时，再把跳过的槽位按「刚好保持占比」的金额买回来，只买回必要的几个。原来超配的槽位，补回目标即可。
   - 没买到的槽位占比仍可能比投入前低，这是被稀释，不是算法出错。
4. 如果金额足够把所有候选补到目标，剩余部分按目标权重分配。
5. 每个槽位推荐一个品种：同币种里**已经持有最多**的那个；都没持有过时，取映射表里的第一个。
6. 结果：列出每一笔的金额和「当前% → 投入后%」，以及投入前后的最大偏离；同时列出低配但没有同币种品种可买的资产。
7. 执行：每个涉及的账户各记一笔入金，再按建议逐笔记买入。

## 取钱算法
1. 投入后总资产 T2 = 当前总资产 − 取出金额。
2. 只在同币种的持仓里卖：每个槽位先卖掉超配部分 = min(该币种持仓, max(0, 当前市值 − 目标% × T2))。
3. 如果超配部分不够，剩余金额按各槽位剩余持仓的比例分摊。
4. 同一槽位内，先卖市值大的持仓。
5. 执行：逐笔记卖出，最后每个涉及的账户各记一笔出金。

## 数据模型（Supabase，全部开启 RLS）
用户数据表都带 `user_id`，RLS 策略为「只能读写自己的数据」。`exposures` 和 `instruments` 例外：`user_id` 为空的行是全局预置，所有人只读，由迁移文件维护；不为空的行是用户自建。按代码查找品种时，用户自建的优先。

**流水是唯一的事实来源。** 持仓、现金、净投入本金都不单独存表，而是把流水按（日期, 创建时间）排序后依次推导出来。推导函数写在 `src/domain/`，App 和 Worker 共用同一份。

- `accounts`：id, name, type（broker / bank）, currency（CNY / USD）, market, color, updated_at
- `exposures`（底层资产）：id, user_id（可空）, name, group, is_stock, updated_at
- `instruments`：code, user_id（可空）, name, market, currency, exposure_id, pays_dividend, updated_at
  - 现金也是品种：代码 `CNY` / `USD`，market 为「现金」，分别归入底层资产「人民币现金」「美元现金」。账户现金就是这个账户里 `CNY` / `USD` 的持有量，一个账户可以同时有两种币的现金
- `transactions`：id, date, created_at, type, account_id, instrument_code, qty, price, fee, reason, fx_to_cny
  - id 由客户端生成（UUID）。流水只增不改，同一笔重复上传也只记一次
  - fx_to_cny：这笔流水的币种兑人民币的汇率，人民币记 1。汇率都联网查询：在线记账直接用当前汇率；离线记账先用最后一次查到的汇率，上传前换成记账当天的实际汇率
  - 每种 type 的含义见下面的「流水类型」
- `targets`：slot_key（底层资产 id 或 'stocks'）, pct；外加 own_stock 标记（个股是否单独设目标）, updated_at
- `plans`：threshold, rebalance_period, calib_period, undefined_mode（sell / ignore：「未定义」资产在再平衡时建议卖出，还是不参与）, annual_spend, target_amount, expected_return, inflation, updated_at
- `snapshots`：date, total_value_cny, net_invested_cny, usd_cny（每天一条，首次录入完成时先写当天的一条；用来画收益曲线）
- `snapshot_items`：date, exposure_id, value_cny（每天每个持有的底层资产一条，用来算「各资产表现」）
- `ai_conversations` / `ai_messages`：会话和消息。AI Key 不入库，只保存在本机

### 流水类型

| type | 记录什么 | 对持仓和现金的影响 | 对本金的影响 |
|---|---|---|---|
| opening（期初） | 首次录入的每条持仓和现金。qty 为份额，price 为平均成本（现金的 qty 为余额、price 为 1）。记录页显示为「期初录入」 | 份额 + qty，成本 + qty × price | + qty × price |
| buy（买入） | qty、price、fee | 份额 + qty，成本 + 金额；同币种现金 − 金额。金额 = qty × price + fee | 不变 |
| sell（卖出） | qty、price、fee | 份额 − qty，成本按平均成本同比例减少；同币种现金 + qty × price − fee | 不变 |
| deposit（入金） | instrument_code 为币种，qty 为金额 | 现金 + qty | + qty |
| withdraw（出金） | instrument_code 为币种，qty 为金额 | 现金 − qty | − qty |
| calibrate（校准） | qty 是券商显示的**实际份额**，不是差额；reason 为红利再投 / 拆股合股 / 手动修正 / 已核对 | 份额改为 qty，总成本不变 | 不变 |

- 表中对本金的影响都要乘 fx_to_cny 折成人民币。组合内部的买卖、校准都不影响本金
- 凡是改变本金的情况，都必须落一条 deposit / withdraw 流水，不能只改数字。记账时自动补记的情况：买入时同币种现金不足（包括跨币种买入）、跨币种卖出、「投入一笔钱」、「取钱」
- 校准存实际份额而不存差额，是为了多台设备离线记账、合并之后，结果仍然等于券商显示的数。记录页显示的差额在推导时算出
- 「各资产表现」用 snapshot_items 计算：某资产的区间收益 = 期末市值 − 期初市值 − 区间内净买入

### 美元视图
每天的总资产按当天快照的 usd_cny 换算；本金按每笔 opening / deposit / withdraw 当天的汇率换算（美元流水直接用原币金额，人民币流水取当天快照的 usd_cny，当天没有快照就取最近一天的）。

### 本地优先与同步
- 手机本地（IndexedDB）存一份完整数据。记一笔等操作先写本地、立即显示，同时放进待同步队列；联网后按顺序上传，失败自动重试。离线时照常记账，行情和汇率先用最后一次查到的值
- 离线记的流水，上传前先联网查记账当天的实际汇率，更新 fx_to_cny 后再上传；暂时查不到就留在队列里，下次同步再试
- App 启动、回到前台、网络恢复时，拉取其他设备新增的流水和改过的设置
- 流水只增不改，多台设备的流水直接合并、重新推导，不会互相覆盖；账户、底层资产、品种、目标组合、计划这些设置按 updated_at，以最后修改的为准
- 记账时按本地推导的结果校验：卖出不能超过持有份额，出金不能超过现金。多台设备合并后如果出现份额或现金为负（很少见），App 里标出来，用「校准」或补记一笔来修正
- 必须联网的只有：登录、刷新行情、AI 投顾

## 修订记录

### 2026-09-29 · 开工前补充
对照原型 v5 的代码逐项核对后补的缺口。原型和本 README 不一致的地方，以本 README 为准。

1. **现金**：原型把现金当作代码为 CNY / USD 的持仓来存，原数据模型没写，现已写明。
2. **账户币种**：第一期只支持 CNY / USD。原型「添加账户」可以选 HKD，但港币现金、港股行情都没有实现，先去掉；HKD 仍可作为显示币种。
3. **流水**：加 `fx_to_cny` 和 `opening` 类型；凡是改变本金的情况都落一条入金 / 出金流水。原型里跨币种买卖只改了本金数字、没写流水，以后从流水重建本金线会漏掉。
4. **美元视图**：快照加 `usd_cny`，按历史汇率换算。原型统一按当前汇率换算，美元曲线只是人民币曲线等比缩放，看不出汇率的影响。
5. **各资产表现**：新增 `snapshot_items`。原模型只存总资产，算不出每个资产在区间内的表现（原型里是模拟数据）。
6. **全局预置数据**：原 README 说每张表都有 `user_id`，BUILD_PLAN 阶段 3 又说 instruments 是公共表；统一为 `user_id` 可空，空表示全局预置。
7. **plans 加 `undefined_mode`**：原型里有「未定义资产建议卖出 / 不参与再平衡」的开关，数据模型里漏了。
8. **离线记账与同步**：改为以流水为唯一的事实来源，持仓、现金、本金都由流水推导，不再单独存 positions 表。这样离线也能记账，联网后自动同步，多台设备的记录合并时不会互相覆盖。校准改为存券商显示的实际份额：原型存的是差额，多台设备合并后会算错。
9. **投入一笔钱 / 取钱**：按账户分别记入金 / 出金。原型只记了一笔，而且记在第一笔交易的账户上。
10. **登录与域名**：登录改为邮箱 6 位验证码，并配置自定义 SMTP；前端和 Worker 绑定自己的域名（在腾讯云买，DNS 交给 Cloudflare）。
11. **「投入一笔钱」的说法更正**：原文说「任何槽位买入后占比都不会下降」，这一点做不到。例如三个槽位当前 39% / 1% / 60%、目标 40% / 10% / 50%，投入总资产的 10%，注水会给第一个槽位 1、第二个 9，第一个槽位投入后是 40 ÷ 110 ≈ 36.4%，比投入前低。现改为可验证的说法：钱不够把所有候选补到目标时，被买入的槽位不会超过目标比例，低配越严重的越先补。
12. **离线记账的汇率**：离线时先用最后一次查到的汇率，上传前换成记账当天的实际汇率。

### 2026-10-03 · 阶段 5
13. **「投入一笔钱」不再稀释被买入的槽位**（用户决定）：BUILD_PLAN 阶段 5 的验收要求「每个槽位买入后的占比都没有下降」，第 11 条的例子正好违反。现在注水给的钱不够保持占比的那几笔不买，改投更低配的槽位：第 11 条的例子里，第二个槽位拿到全部 10，正好到目标 10%。更低配的放不下（会超过目标）时，把跳过的槽位按「刚好保持占比」的金额买回来。原来超配的槽位，要保持占比就得超过目标，所以只补回目标，占比会降到目标为止。钱足够把所有候选补到目标时（第 4 步），算法不变。
14. **AI 请求不经过 Worker**（阶段 6，用户决定）：原文说连通性测试和对话请求都通过 Worker 转发，理由是避免浏览器跨域限制。2026-10-03 核实，DeepSeek 允许我们的网址直接调用 `/models` 和 `/chat/completions`（错误响应也带跨域头），这个理由不成立。改为浏览器直连：Key 不经过我们的服务器，正好符合「Key 只加密保存在本机」；国内直连也更快。以后接入不允许跨域的服务商时，再加 Worker 转发。
